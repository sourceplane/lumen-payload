# lumen-payload-cms — implementation plan

Milestones land in order. Each is one task, each task one pull request on an
`orun/PC-<n>-<slug>` branch with an `Orun-Task: PC-<n>` trailer on every
commit and the manifest block in its body. A pull request merges only when
every check is green — on these branches CI runs **every** lane, not just
`plan` — and a milestone is marked ✅ here when its "done when" list is true on
the live system, then recorded in `IMPLEMENTATION-STATUS.md`.

## PC0 — the spec

This doc set and `tasks/PC-1.TaskContract.yaml`, merged to `main`.

**Done when**
- the five documents are on `main`

## PC1 — the CMS database path

`infra/terraform/cloudflare-hyperdrive-cms`: a copy of `cloudflare-hyperdrive`
with its own state, its own name (`<reponame>-cms-<env>`), `caching.disabled =
true`, the same self-healing adoption, and a `random_password` for Payload.
`secretOutputs` publishes `WIRING_CLOUDFLARE_HYPERDRIVE_CMS=wiring` and
`CMS_PAYLOAD_SECRET=payload_secret`. Nothing reads them yet.

**Done when**
- the PR's plan-only lanes for stage and prod are green
- the merge's apply lanes for stage and prod are green
- `cloudflare-hyperdrive` is not in either plan (untouched)

## PC2 — the CMS schema

Migration `200_cms_payload_core` in `packages/db/src/migrations`, its manifest
entry and checksum. Generated from the PC3 configuration (design §2) and
committed ahead of it, so the schema exists before anything reads it.

**Done when**
- `db-migrate` plans the migration on the PR and applies it on stage and prod
  after the merge
- no other migration's checksum changed

## PC3 — the CMS on Workers

`apps/cms` (Payload 3.89.0, Next 16.3.3, OpenNext) as a
`cloudflare-worker-turbo` component with `dependsOn` on
`cloudflare-hyperdrive-cms` and `db-migrate`, its own isolated lane,
`runtimeSecrets` for `PAYLOAD_SECRET` and `CMS_SETUP_TOKEN` (pushed by
`secrets-live`), and a `smokeCommand` on `/health` and `/admin`. The setup gate
(design §4) and the request-scoped pool (design §3). `tests/cms` as a
`turbo-package` suite on the `verify` profile. `pnpm-lock.yaml` regenerated by
`pnpm install`. Needs the Cloudflare account on Workers Paid (PC-H).

**Done when**
- every lane of the PR is green, including the CMS build, typecheck and
  `wrangler deploy --dry-run`, and every other component's lanes
- after the merge, on stage and prod: `/health` answers `{"status":"ok","db":"ok"}`,
  `/admin` answers 200, and an anonymous `POST /api/users/first-register`
  answers 403

## PC4 — media on R2 (gated)

A `cloudflare-r2-cms` terraform component (one bucket per environment), an
`R2_MEDIA` binding, `@payloadcms/storage-r2`, a `media` upload collection and
migration `205_cms_media`.

**Gated** on a Cloudflare token minted with the `r2-data` template: the
brokered `workers-deploy` token is "Workers Scripts and KV … no R2" (the
platform's own template table), so no existing secret can create a bucket. The
owner mints `CLOUDFLARE_R2_TOKEN` once; nothing else blocks on it.

**Done when**
- the bucket exists on stage and prod
- an image uploaded through `/admin` is served back from `/api/media/file/…`

## PC5 — the record

`ai/context/operations.md` gains a CMS section (the owner steps of design §4,
the verify commands of §5); `apps/cms/docs/{overview,architecture,runbook}.md`
and the same three for the new terraform component; `AGENTS.md`'s layout lists
the CMS; `IMPLEMENTATION-STATUS.md` reads shipped and names every departure.

**Done when**
- the owner can open the admin from `operations.md` alone
- the status file is complete

## Sequencing note

PC1 before PC3 because the CMS's deploy reads the wiring PC1 publishes; PC2
before PC3 because the CMS must never start against a missing schema, and
because it makes the schema reviewable on its own. PC3 declares both as
`dependsOn`, so even a re-run of everything converges in the right order. PC4
is independent of PC5 and waits only on the owner's token; PC5 lands after
PC3 whether or not PC4 has.
